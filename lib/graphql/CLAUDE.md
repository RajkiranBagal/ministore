# lib/graphql/ — Schema, builder, context, client

The GraphQL layer. The HTTP endpoint that serves it is `app/api/graphql/route.ts`.

| Module | Exports | Purpose |
|---|---|---|
| `builder.ts` | `builder` | Pothos `SchemaBuilder` wired to the Prisma plugin. |
| `schema.ts` | `schema` | Types + queries; `builder.toSchema()`. |
| `context.ts` | `createContext`, `GraphQLContext` | `{ userId }` from `await auth()`. |
| `client.ts` | `gqlRequest<T>(query, variables?)` | ⚠️ **Browser-only** — relative URL. |

## Things that will bite you

- **Prisma 7 requires `dmmf: getDatamodel()`** in the builder's `prisma` options. Prisma 7 removed the DMMF from the client internals, so the Pothos plugin can no longer find it by itself. Omitting it fails at runtime, not at compile time.
- **A `prisma-pothos-types` generator block lives in `prisma/schema.prisma`**, output `../lib/generated/pothos/index.ts` (gitignored, regenerated by `prisma generate`). The `/index.ts` suffix is required — pointing `output` at a bare directory makes Prisma write a *file* named `pothos`, and its internal `../prisma/client` import then resolves to the wrong path.
- **Self-referencing fields must use the model-name string**, e.g. `t.prismaField({ type: ["Product"] })`, not the `ProductType` variable. Naming the type inside its own definition trips TS7022 circular inference; Pothos resolves named types lazily. Conversely, a plain `t.field` **cannot** take a model-name string — only `prismaField` can — so `ProductPage.products` uses `[ProductType]`.
- **`stock` and `createdAt` are deliberately not exposed**, matching the REST DTO. A GraphQL schema is if anything easier to over-share through, since clients can ask for anything you declare.
- **GraphQL validates types but not ranges.** The `products` resolver clamps `page` and `limit` itself (limit capped at 50) — the schema won't do it for you.
- **`gqlRequest` is not Apollo and shouldn't become Apollo** until something actually needs a normalised cache. Note it checks *both* `res.ok` and `body.errors`: GraphQL returns HTTP 200 for query errors.

## The `related` field — the point of the whole exercise

`Product.related` is the one thing REST couldn't do as neatly: the FastAPI service supplies the **ranking**, Postgres supplies the **data**, and the client sees one query.

- Rows are re-read from Prisma via a single `findMany({ id: { in: ids } })` — **not N+1** — then re-sorted back into the service's ranking, since `findMany` returns arbitrary order.
- Upstream URL is `RECOMMENDATIONS_API_URL` — **server-only, no `NEXT_PUBLIC_` prefix**. Moving it here is what removed the service URL from the client bundle and removed the CORS requirement from the Python service.
- 3 s `AbortSignal.timeout`, and any failure logs `graphql.related.failed` and returns `[]`. A second service being down must never fail the product query.
